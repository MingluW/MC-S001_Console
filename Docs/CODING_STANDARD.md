# MC-S001 Console 代码规范与结构

版本：1.0；日期：2026-10-28。

本文规定后续手写代码的目标结构。现有工程尚未完成分层，不得将本文中的规划描述为已经实现。
原则：看名字知道职责，看入口知道流程，新增模块不需要修改无关模块。

## 1. 目录与依赖

```text
USER/
  src/
    main.c                    N32Cube 初始化、App 调用入口
    n32h47x_48x_cfg.c          生成的初始化
    n32h47x_48x_it.c           生成的中断入口
    App/                      应用源文件
      app.c                   初始化及主循环调度（已实现）
      app_control.c           统一状态变更入口（已实现显示演示）
      app_display.c           根据只读状态组织显示（已实现）
      app_selftest.c          板卡验证（规划）
    Board/                    板级源文件
      board_led.c             LED501 开关（已实现）
      board_time.c            毫秒时基（已实现）
      board_uart.c            USART2调试口、缓冲收发（已编码，待实板验证）
      board_stdio.c           printf重定向及有界libc堆（已编码）
      board_lcd_port.c        LCD GPIO 9位接口（点亮通过）
      board_spi.c             通用硬件SPI（按需规划）
      board_can.c             CAN（规划）
      board_keys.c            六路面板键原始输入（已实现）
    Modules/                  功能源文件，按需建立
      log/                    ERR/WARN/DBG日志（已编码）
      keys/                   六键消抖、加减连发、停止优先（已实现）
      lcd/                    初始化、完整帧提交、速度数字段码（已实现）
      powerboard/             下控编解码、通信状态机
      pc_protocol/            上位机协议
      buzzer/                 蜂鸣器时序
  inc/                        全部手写头文件集中存放，保留生成的头文件
    app.h
    board_led.h
    board_time.h
    board_pins.h              引脚与有效电平定义
    ...                       后续 keys.h、lcd.h 等按需加入
Driver/                       厂家 SDK，保持原目录和头文件位置
Makefile/                     构建、链接及下载脚本
Docs/                         规范、状态和验证记录
```

- 用户约定：手写 `.c` 在 `USER/src` 下按 App、Board、Modules 分目录，手写 `.h` 全部直接放在 `USER/inc`。SDK 自带头文件保持原位置，不搬入 inc。
- 头文件名必须全工程唯一，并带模块含义；不要给每个模块再建立 src/inc。
- 依赖方向：App 可以调用 Modules、Board；Modules 可以调用 Board；Board 可以调用 SDK。
- 协议编解码核心只依赖标准 C 类型和必要的本模块头文件，不依赖 MCU、显示或应用状态。
- Board 不包含 App/Modules 头文件；LCD 不包含下控协议或业务命令定义。
- `USER/src/main.c` 是装配入口，负责保留生成初始化并调用 App；中断入口允许调用相应 Board ISR 处理函数。
- 避免创建万能 `common.c`、`utils.c` 或不明确职责的 `manager.c`。

## 2. 模块职责

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| Board UART/SPI/CAN | 外设传输、缓冲、硬件错误 | 业务命令、UI、产品状态 |
| Keys | 原始输入识别为统一事件 | 加减速度、发通信命令、刷新显示 |
| LCD | 初始化、段码/图形数据、提交显示 | 启停、风扇控制、回复上位机 |
| Powerboard | 报文、事务、心跳、超时和链路状态 | 直接修改 AppState、直接操作 LCD |
| AppControl | 统一业务入口、参数约束、处理执行结果 | 外设寄存器操作 |
| AppDisplay | 根据状态组织显示 | 改变运行控制状态 |

GPIO 按键、扩展按键、上位机输入应映射到同一套应用动作，业务规则只维护一份。
模块之间优先使用明确函数、返回值和有界事件队列；确有需要才引入回调，不预先构造通用消息框架。

## 3. 运行模型与时间

- 默认裸机协作式主循环，每轮调用各模块 `Process()` 或 `Poll()`；单个模块统一一种命名。
- App_Process 只组织任务调用；各任务的到期判断和提前 return 留在任务函数内部，不能因一个任务未到期跳过其余任务。
- 时间由 `BoardTime_Millis()` 提供。每轮获取时间并传给需要计时的模块，便于测试。
- 用 `(uint32_t)(now_ms - last_ms) >= interval_ms` 判断间隔；不直接用 `now_ms >= last_ms + interval_ms`。
- 常规间隔应远小于计时器回绕周期；采用有符号差判断绝对期限时，期限跨度必须小于 2^31ms。
- 不在运行主循环里等待按键释放、安全锁恢复、通信响应或测试模式退出。
- 启动阶段必要的屏幕复位/上电延时可以阻塞，必须说明原因、最长时间及此时是否需要服务通信。
- 短小 SPI 同步传输可以使用有超时的轮询；不能写没有超时的硬件忙等待。
- 通信接收处理每轮设置有限预算，避免持续数据流长期占用主循环；刷新时长随实际硬件测量后记录。
- 暂不引入 RTOS；出现明确并发或时序需求时再评估，不为目录分层引入 RTOS。

## 4. 命名与格式

- 手写代码使用 C99 可用语法，不依赖 C++；使用 `<stdint.h>`、`<stdbool.h>`、`<stddef.h>`。
- 文件使用小写下划线：`board_uart.c`、`app_control.c`；大小写保持一致。
- 公共函数使用模块前缀：`BoardLed_Set()`、`Keys_Process()`、`Powerboard_Request()`、`AppControl_Start()`。
- 私有函数和变量使用小写下划线：`decode_frame()`、`last_scan_ms`；私有函数及文件级状态加 `static`。
- 类型使用模块前缀和有意义的名称，例如 `KeysEvent`、`PowerboardStatus`、`AppState`；枚举值和宏使用大写下划线及模块前缀。
- 变量表达含义和单位：`target_speed_x10`、`timeout_ms`、`length_bytes`；速度的具体单位由协议确认后统一。
- 禁止用 `flag1`、`temp2` 等含糊名字长期承载模块状态；布尔值用 `is_`、`has_`、`pending` 等明确词义。
- 4 空格缩进，花括号独占行；手写代码尽量不超过 100 列。Makefile 配方保留 Tab。
- UTF-8 编码；解释和维护说明优先中文，标识符英文。不要自动重编码全部 SDK 或生成文件。
- 不为了格式统一重排厂家代码；新增手写代码遵循本文。

## 5. 头文件与接口契约

- 头文件使用 include guard，能够被单独包含；只包含声明所需依赖。
- `.c` 先包含自己的 `.h`，再包含标准库和其他依赖。
- 头文件不定义可写全局对象；共享常量表需要时在 `.c` 定义，通过声明或接口访问。
- 每个公共接口说明：用途、参数/单位、返回值、是否阻塞、是否可在 ISR 调用。
- 涉及缓冲区时必须说明：容量、有效长度、所有权、指针是否被保留以及数据有效期。
- 异步发送入队默认复制数据；若使用零拷贝/DMA，明确缓冲区在完成前不得修改或释放。
- 返回结果不能含糊地混用 0/1。只有单纯成功/失败用 `bool`；忙、满、无效、超时等用模块枚举。
- 读取接口分别表达“暂时无数据”和“硬件错误”；不能把两者默默合并。
- 应用级接口隐藏 MCU 类型；MCU 寄存器、GPIO 端口等类型仅出现在 Board、生成代码和 SDK 内。

## 6. 状态、队列与并发

- AppState 只描述产品状态；按键消抖、协议重试、显示缓存各由本模块管理。
- AppControl 管理控制状态的变更；其他模块通过结果/事件上报，显示层读取状态或快照。
- 区分目标值、实际反馈值和待确认状态。入队或发送成功不代表下控执行成功。
- 队列满、通信未就绪时不能清除尚未成功提交的待发送标志。
- 使用固定大小数组和队列，明确满时返回失败、丢新或覆盖旧数据的策略，并记录溢出统计。
- 停止/故障等事件不能静默丢弃；按业务要求确定优先级及队列策略。
- 避免运行期间 `malloc/free`；若后续确有必要，先记录用途、容量和失败处理。
- ISR 与主循环共享数据，按需要使用 `volatile`，但不能认为它保证复合操作原子性。
- 环形缓冲明确生产者/消费者；必要的临界区只保护短小数据操作，不包围日志或传输。
- 中断内不做格式化打印、协议解析、LCD 刷新、延时或业务状态机。

## 7. 协议、UART、CAN 与显示

- 明确区分 UART 字节层、协议帧层、请求/响应事务层和应用动作层。
- 收包必须校验最短长度、声明长度、最大长度、校验和/CRC和命令参数，再访问字段。
- 多字节值显式编解码端序；不将接收字节直接强转结构体，不依赖结构体布局或主机端序。
- 调试串口与下控链路职责分开，不能将日志输出混入业务报文。
- 本工程使用USER/inc/log.h的ERR/WARN/DBG，支持printf格式、时间和级别过滤。
  仅主循环使用，入队失败按场景处理；接线、容量和返回值见Docs/UART_LOG.md。
- CAN 提供 ID、标准/扩展帧、有效长度和载荷等帧接口；不把 UART 字节协议原样套到 CAN。
- CAN FD 的报文映射、DLC、波特率、分包及超时必须按后续确认的协议实现。
- 段码 LCD 优先拆为屏幕驱动、段码映射、应用显示；图形屏确认后再引入字体/绘图接口。
- 显示缓存由显示模块持有，内容变化后再提交；是否局部刷新/DMA依实际屏幕需要决定。
- 日志标注模块，重点记录状态变化和错误；常规循环不刷屏，原始报文跟踪可开关。

## 8. N32Cube 与构建维护

- 不在 `NTFx CODE START/END` 自动生成区域写手工业务代码，生成区以生成器维护为主。
- App 调用、必要 include 等接入点放在生成区外，但不能假定生成器一定保留；重生成必须比较文件。
- 保留 `.ntfx` 配置作为配置源；记录 Board 所用的外设初始化属于生成配置还是手工适配，避免重复初始化。
- 新目录默认不会被当前 Makefile 自动编译；添加模块必须显式补充源码目录和头文件目录。
- 当前对象文件按源文件 basename 放进同一个 build 目录，所以所有参与编译的 `.c` basename 必须唯一。
- 备份、参考工程、自测专用程序不得被通配符误编译；一个固件只有一个 `main()`。
- 新配置需同步 `.vscode` 代码分析路径；保持 `Ctrl+Shift+B`、J-Link 调试和 `make download` 可用。
- 保留 8 字节对齐的初始栈地址，以及具体芯片容量；不使用系列最大容量代替具体型号。
- 重新生成后重点检查 Makefile、自定义目录、链接脚本、main 接入点、VS Code 和 J-Link 脚本。
- 不修改 SDK 解决应用问题。确需修改时，记录文件、原版本/来源、原因和差异。

## 9. 验证与交付

- 只验证本轮变更相关内容。普通格式/文档修改不强制新增测试。
- 代码重构至少编译通过，并检查新文件确实纳入构建；不能只靠编辑器没有红线。
- 协议、按键、超时/重试等逻辑应增加有意义的边界验证，例如错误CRC、半包、队列满、计时回绕。
- 纯逻辑尽量可在主机测试；硬件驱动需要板上验证，二者不能相互替代。
- 建立功能后记录：配置、操作、期望现象、实际结果及未覆盖范围。
- 发现既有警告先确认来源，禁止通过全局关闭警告掩盖新问题。
- 文档和状态记录保持真实：已规划、已编码、已编译、已烧写、实板验证通过分别记录。

## 10. 当前实施顺序与待定项

实施顺序：App/Board 基础与非阻塞 LED → 调试 UART → Keys → SPI/LCD → CAN 与下控协议。
每步形成可独立验证的版本，保留用户当前闪灯亮灭各 1500ms 的行为，除非用户明确要求改变。

已确认LCD与Cypress方案完全相同，旧初始化移植点亮通过，后续独立段码显示逐项验证。
待定项：UART 和 CAN 各自的用途；新下控报文协议；
CAN/CAN FD 波特率与ID分配；按键具体短长按规则；控制命令确认及故障恢复规则。
这些事项不阻碍目录和模块边界先确定，但不得猜测为已确认的产品需求。
